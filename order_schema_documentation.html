1. Overview — Why We Normalised

The original orders table had grown to 50+ columns mixing five separate concerns into one row:

ConcernColumnsProblem
Core order datastatus, subtotal, shipping, coupon …OK — stays in orders
Payment gatewaygateway_order_id, gateway_payment_id, gateway_signature, gateway_response …One order can have multiple payment attempts (e.g. first try fails). A single column per order cannot model this. → moved to payments
Refund trackingrefund_amount, refund_status, refund_note, refund_bank_details …An order can have multiple refund events (partial cancel + later return). A single refund_amount can only represent one event. → moved to order_refunds
Reverse logisticsshiprocket_return_order_id, shiprocket_return_awb, shiprocket_exchange_awb …Each return/exchange action generates its own shipment. These belong on order_item_actions, not on the order. → moved to order_item_actions
Derived timestampsreturn_requested_at, exchange_requested_atDirectly derivable from order_item_actions.created_at. → deprecated (derived)
Result after normalisation The orders table drops from ~50 columns to ~30 meaningful columns. Each concern has its own table with clean foreign-key relationships and the ability to have multiple rows per order where the business logic requires it.

3.3  payments NEW TABLE

One row per payment attempt for an order. A prepaid order whose first attempt failed will have two rows (one Failed, one Paid). A COD order has one row starting as Pending and updated to Paid when the seller confirms collection.

This table replaces the gateway_* columns that previously lived on the orders table.

order_id FKINTEGER✗—Parent order
payment_methodVARCHAR✗CODCOD or Prepaid
payment_gatewayVARCHAR✓NULLrazorpay, phonepe, or NULL for COD
gateway_order_idVARCHAR✓NULLRazorpay/PhonePe order object ID used to verify signature
gateway_payment_idVARCHAR✓NULLRazorpay payment ID (e.g. pay_XYZ). Also used for idempotency dedup on createOrder.
gateway_signatureTEXT✓NULLHMAC-SHA256 signature verified server-side before order is confirmed

amount_paiseINTEGER✓NULLAmount × 100 (paise) — what was sent to the gateway for cross-check
currencyVARCHAR✗INRCurrency code
statusVARCHAR✗InitiatedInitiated → Paid / Failed; then Refunded / Partially Refunded
failure_reasonTEXT✓NULLSet if status = Failed
gateway_responseJSONB✓NULLFull gateway webhook/callback payload for audit and debugging
verified_atTIMESTAMP✓NULLWhen the server-side signature check passed
created_at, updated_atTIMESTAMP✗NOW
Why one payments row per attempt, not per order? A customer may start payment, face a bank timeout (status = Failed), and retry successfully (status = Paid). Storing both rows gives a complete audit trail instead of overwriting the failed attempt. The order confirmation only fires on the successful Paid row.

4. Data Flows

4.1  Order placement (Prepaid)

Validate stock — Lock product rows (SELECT FOR UPDATE), validate all items have enough stock and are active. Return 400 on first failure before any writes.

Verify payment — Server-side HMAC-SHA256 check of gateway signature. Amount in paise is cross-checked against the expected total.

Apply coupon — Find coupon, check usage limit, calculate discount, increment coupons.usage_count.

Debit wallet (if used) — Decrement customers.wallet_balance, create wallet_transactions row.

Create order — INSERT into orders with all pricing, snapshot address, status = Pending, status_history = [{Pending}].

Create order items — INSERT one row per cart line into order_items with price snapshot and per-item shipping_meta.

Decrement stock — Update products.stock_quantity and products.color_stocks[colorId].

Create payment record — INSERT into payments with gateway IDs, amount_paise, status = Paid, verified_at = now.

COMMIT — Fire-and-forget: send confirmation email + push to ShipRocket.

COD variation

Same flow except: no signature verification. COD-block check is done first. The payments row is created with status = Pending (no gateway fields set).

4.2  Full cancellation within 24 h

Preconditions Order must be: within 24 hours of creation, not yet shipped, is_modified = false, and in a cancellable status (Pending / Processing / AWB Assigned).

Check guards — Fail if is_modified is true, or 24 h window has passed, or order is shipped.

Update all order items — Set status = Cancelled, cancelled_quantity = quantity for every item.

Restore inventory — Increment stock back for each item.

Decrement coupon — If a coupon was applied, decrement coupons.usage_count by 1.

Update order — Set status = Cancelled, cancelled_at = now, append to status_history.

Create OrderRefund (Prepaid only) — INSERT into order_refunds: refund_type = full_cancel, amount = payable_amount, status = Pending, payment_method = original_gateway. For COD: status = Not Required.

Update payment record — Set payments.status = Refunded.

4.3  Partial cancellation / quantity decrease within 24 h

This can only happen once. After a partial cancel, orders.is_modified is set to true. Any further cancel or update attempt is rejected with a clear error message.

Check guards — Fail if is_modified is already true.

Calculate new subtotal — Subtract the cancelled item's price × quantity from orders.subtotal_amount.

Recalculate coupon — Re-apply the coupon percentage/fixed discount against the new subtotal. If the new subtotal falls below the coupon minimum or the coupon is no longer found, the discount is removed entirely. Cap percentage coupons at max_discount_amount.

Recalculate total — newTotal = newSubtotal + fixedCharges − newCouponDiscount − walletUsed. Fixed charges (shipping, fees) do not change.

Calculate refund — refundAmount = paidAmount − newTotal.

Update order item — Increment cancelled_quantity. Set status = Cancelled or Partially Cancelled depending on remaining units.

Restore inventory — Add back the cancelled units to product stock.

Update order — Set subtotal_amount, discount_amount, payable_amount to new values. Set is_modified = true, modified_at = now. Append "Partially Cancelled" to status_history.

Create OrderRefund (Prepaid only) — INSERT with refund_type = partial_cancel, amount = refundAmount, status = Pending.

4.4  Return after delivery

Precondition: Order must be in Delivered status. Return window is configurable (typically 7 days after delivery).

Create OrderItemAction — INSERT with action_type = return, status = Requested. Set order_items.pending_action_quantity += quantity.

Calculate estimate — estimatedRefund = itemAmount − forwardShipping − reverseShipping. Shown to customer before they confirm.

Admin approves — Update action status = Approved. Arrange reverse pickup via ShipRocket. Store shiprocket_return_order_id and shiprocket_return_awb on the action row.

Courier picks up — Admin updates action status = Completed. order_items.returned_quantity += quantity. pending_action_quantity -= quantity. Set completed_at = now.

Create OrderRefund — INSERT with refund_type = return, amount = estimated_refund_amount, status = Pending.

Process refund — Admin marks refund as Completed, sets gateway_refund_id or bank_details, sets processed_at.

4.5  Exchange after delivery

Create OrderItemAction — INSERT with action_type = exchange. meta.exchange_target stores the desired replacement product/colour. Set pending_action_quantity += quantity.

Admin approves — Arrange reverse pickup (shiprocket_return_awb stored on action row). Simultaneously create a new forward shipment for the replacement item.

Both shipped — Update action status when reverse parcel arrives. order_items.exchanged_quantity += quantity. pending_action_quantity -= quantity. completed_at = now.

Create OrderRefund — INSERT with refund_type = exchange, amount = 0, status = Not Required (no money changes hands).

Why does an exchange create an OrderRefund row with amount = 0? The order_refunds table is a complete audit log of every financial decision, not just money-out events. A row saying "exchange — Not Required" gives the admin a clear record that this was assessed and intentionally has no monetary component.

4.6  RTO (Return to Origin)

This happens when the courier fails to deliver the order to the customer (usually after 3 attempts) and ships it back to the seller.

ShipRocket webhook / admin action — Admin updates order status to "RTO Delivered".

Calculate RTO refund — rtoRefund = payableAmount − (forwardCharge + rtoCharge) × rtoCount − redispatchPaid. Values come from orders.selected_courier_data.

Update order — Set is_rto = true, rto_count += 1, customer_cod_blocked = true (on order), append to status_history.

Block customer COD — Set customers.is_cod_blocked = true. All future COD attempts by this customer (by email + phone match) will be rejected.

Create OrderRefund — Prepaid: refund_type = rto, amount = rtoRefund, status = Pending. COD: amount = 0, status = Not Required.

Optional re-dispatch — Admin can create a new order from the returned stock with is_redispatched = true and original_order_id pointing back. Customer pays again (or via COD after review).
